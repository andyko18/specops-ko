> **성격**: 6회에 걸친 `docs/audit/` 평가 시리즈와 **다른 문서**다. 시리즈는 고정 5축·고정 가중이라

## 2. 진단 — "불편"의 정체는 false-deny다

### 2.1 ★ 러너 인식 정규식이 4사본 중 1사본만 고쳐졌다 (신규 발견)

PR #26(`377e3be`, 09-03)은 "false-block 10호"를 고치며 커밋 메시지에 **스스로 이렇게 적었다**:

> *3사본 동시 수정 (부분 수정 시 "실행은 되는데 커밋이 막힌다" 무음 비대칭)*

그런데 실측하면 **`hooks/governance-lib.sh`는 1줄만 바뀌었다**(`_extract_declared_cmds`의 whitelist,
203행). 같은 파일 안에 **transcript 러너 앵커 정규식이 258 · 276 · 418 · 453행 네 곳에 문자열 복제**돼
있고 **그 넷은 전부 옛 패턴 그대로다**. 즉 커밋 메시지가 경고한 그 무음 비대칭이 **지금 살아 있다.**

현행 앵커 정규식에 실제 러너 명령을 넣어본 결과:

| 명령 | 판정 |
|---|---|
| `pytest -q` | 인식 |
| `npm run test:unit` | 인식 |
| `pnpm test` / `go test ./...` | 인식 |
| `bash scripts/run-verification.sh` | 인식 |
| **`poetry run pytest tests/ -q`** | **미인식 → deny** |
| **`python3 -m pytest`** | **미인식 → deny** (정규식은 `python -m` 만 안다) |
| **`pnpm --dir frontend test chart`** | **미인식 → deny** |
| **`pnpm --filter web test`** | **미인식 → deny** |
| `uv run pytest` · `npx vitest run` · `jest` · `make test` | **미인식 → deny** |

**14종 중 8종 미인식.** 그리고 미인식되는 쪽이 하필 하류 실사용의 주류다 — Argus·gobiseo는 poetry,
Argus 프론트·ssl-portal은 pnpm 워크스페이스다.

**귀결이 BYPASS 로그에 그대로 적혀 있다.** Argus `20260902-us-universe-sync` 한 FID에서 6건:

> *"implement 중간 커밋 — T3 receipt PASS(fresh) · staged 는 T3 outputs · 925 passed.
> **FID 러너는 T5·T6 미착수라 지금 FAIL 하며 그것이 R-1 이 존재하는 이유다**"*

사용자가 테스트를 925개 통과시키고, receipt를 남기고, 그 사실을 사유란에 적으면서 우회하고 있다.
**이건 규율 위반이 아니라 도구가 사실을 못 보는 것이다.**

**조치**: 258·276·418·453행의 정규식을 203행과 동일한 커버리지로 올린다. 리터럴 4중복이 문제의 원인이므로
**변수 1개로 추출**한다(현재 `T25`가 "4사본이 서로 같음"을 잠그고 있는데, 그 테스트는 동일성만 보장할 뿐
**넷이 함께 낡는 것은 막지 못한다** — 그 사실이 이번에 증명됐다).

**비용** 소(정규식 1곳 + 회귀) · **효과** 큼 · **위험** 낮음(넓히는 방향이지만 `VERIFY: PASS` 양성 요구는 불변)

### 2.2 R-1이 incremental TDD와 구조적으로 충돌한다

`_verify_exec_evidence`는 **`tasks.md ∧ evidence.md`가 둘 다 있을 때만** 선언 명령 경로(`decl`)를 연다
(주석: *"evidence.md 부재(implement 창)는 task receipt 소관"*). 그런데 implement 중간 창은:

- evidence.md가 **아직 없다** → 선언 경로 닫힘 → 하드코딩 앵커 5종만 남음 → §2.1의 8종 미인식이 직격
- FID 전체 러너는 **정상적으로 FAIL한다** — 미착수 태스크의 테스트 파일이 아직 없으므로

**즉 TDD를 성실히 할수록 R-1이 더 자주 막는다.** receipt 탈출구가 설계돼 있지만 실사용에서는
BYPASS가 이겼다(같은 FID 6연속). 탈출구가 작동했다면 사유란에 "receipt PASS"라고 쓰면서 우회할 이유가 없다.

**조치 후보**: implement 창에서 R-1의 판정 대상을 **FID 전체 러너 → 해당 태스크의 receipt + 변경 스코프**로
바꾼다. 이건 완화가 아니라 **질문을 바로잡는 것**이다 — "아직 안 만든 기능의 테스트가 통과하는가"는
implement 중간에 물으면 안 되는 질문이다.

### 2.3 ★ docs-only 면제가 실사용 커밋 형태에서 발동하지 않는다 (신규 발견 · 실측 확정)

BYPASS 표본 30건 중 다수가 사유란에 **"코드 변경 0"**이라 적혀 있고, posttool은 그것을
`scope_class: docs-only`로 분류했다. **분류가 docs-only라면 pretool도 면제했어야 한다.**
왜 안 됐는지를 `_commit_scope_is_staged`(면제 스코프를 staged로 좁히는 화이트리스트)를 직접 호출해 갈랐다:

| 커밋 형태 | 판정 |
|---|---|
| `git commit -m "docs: x"` | staged 축소 O (면제 가능) |
| `git commit -F - <<EOF …` | staged 축소 O (면제 가능) |
| **`git add <파일> && git commit -m …`** | **보수 = working-tree 전체 판정** |
| **`cd <경로>` ⏎ `git commit -m …`** | **보수 = working-tree 전체 판정** |
| **`MSG=…` ⏎ `cat > "$MSG" <<EOF` ⏎ `git commit -F "$MSG"`** | **보수 = working-tree 전체 판정** |
| `git add -A && git commit` · `git commit -am` | 보수 (의도된 차단 — 정당) |

**아래 세 형태가 BYPASS 로그에 실제로 나오는 커밋 형태의 대다수다.** Argus·gobiseo·auto-company 로그를
그대로 인용하면 `cd /Users/andyko/Project/0.Claude/Argus` ⏎ `git commit -q -F - <<'EOF'`,
`git add .specops/memory/decisions.md && … git commit`, `MSG=/private/tmp/…` ⏎ `cat > "$MSG"` ⏎
`git commit -q -F "$MSG"` — **셋 다 보수 판정으로 떨어진다.**

보수 판정이면 working tree에 남은 무관한 코드 dirty 때문에 `.specops/` 문서만 커밋해도 차단된다.
**사용자가 방어적으로 BYPASS를 붙인 게 아니라 실제로 막힌다.**

> 이 결함은 이미 한 번 고쳐진 적이 있다 — `20260813-r1-docs-only-scope`가 *"실측 BYPASS 16건 중
> 13건이 '코드 변경 0'"* 을 근거로 staged 축소 경로를 넣었다. 화이트리스트 접근 자체는 옳다(위험 형태
> 나열은 3회 실패했다고 주석이 기록한다). **다만 화이트리스트가 두 형태(`cd` 선행 · 명시 `git add &&`)를
> 빠뜨렸고, 그 둘이 하필 실사용 주류다.**

**전수 분류가 이 진단을 확정한다** — BYPASS 134건 중 **`cd` 선행 47% + 순수 `VAR=` 선행 20% = 67%**가
위 표의 "보수 판정" 칸에 들어간다. 다만 **실제로 회수되는 것은 그중 34%(모집단 조정 47%)** 다 —
prelude 전체가 안전 클래스여야 하고, `git add`·`python3`·`cat`·`pnpm` 등 실제 명령이 선행하는 경우는
**정당한 보수 판정**이라 회수 대상이 아니다.

**조치 (두 갈래로 나눈다 — 안전 등급이 다르다)**:

**C-1 (안전 · BYPASS의 34% 커버)**: 화이트리스트에 **index를 바꾸지 않는 선행**을 추가한다 —
`cd <경로>` 선행 줄과 bare `VAR=값` 대입 줄, 이 **둘만**. staged를 건드리지 않으므로 훅 시점의
`git diff --cached`가 **곧 커밋 범위**라는 전제를 깨지 않는다.
단 `cd` 대상이 다른 repo면 판정 repo가 바뀌므로, **cd 경로가 현재 repo 내부일 때만** 인정하는 가드가 필요하다.

**`cat > <파일> <<EOF …` 블록은 범위 밖으로 뺀다.** 받아들이면 **delimiter 추적을 떠안는데**, 코드 주석이
그것을 명시적으로 거부했고(*"`<<EOF`·`<<'EOF'`·`<<-EOF` 파싱 표면만 늘고 보안 이득이 없다"*),
인용 상태기계는 과거 **두 번 뚫렸다**. heredoc 본문에 `git add -A` 같은 줄을 심을 수 있다.
회수율을 낮추더라도 이쪽이 안전한 기본값이다.

**C-2 (별건 · 3% · 화이트리스트만으로는 무효)**: `git add <경로> && git commit`은 다르다.
**pretool은 명령 실행 전에 발화하므로, 훅 시점의 `git diff --cached`에는 `&&` 체인이 곧 추가할 파일이 없다.**
빈 트리 재현으로 확인했다:

```
[커밋 명령] git add a.md && git commit -m 'docs'
훅 시점 git diff --cached --name-only → (비어 있음)
실제 커밋 범위                        → a.md
```

빈 staged는 `is_docs_only_change`에서 `[ -z "$files" ] && return 1`(fail-safe 비면제)로 떨어지므로
**false-open은 나지 않는다** — 대신 **화이트리스트에 넣어도 아무것도 열리지 않는다.** 제대로 고치려면
`git add`의 명시 경로를 파싱해 `cached ∪ add대상`으로 판정해야 하고(`-A`·`.`·`-u`·`--all` 제외),
그건 C-1보다 복잡하고 위험하다. **빈도가 3%이므로 미루고, 대신 "add와 commit을 별도 호출로 나누면
지금도 통과한다"를 규약으로 안내한다**(단독 `git commit -m`은 위 표에서 이미 staged 축소 O).

추가로, 규칙이 복잡한 것 자체는 남는다. **커밋 전에 "이 커밋은 면제됩니까"를 답해주는 1줄 조회**
(`SPECOPS_DRYRUN=1`)를 함께 넣는다 — 규칙을 단순화할 수 없다면 최소한 조회 가능해야 한다.

**비용** 소~중 · **효과** 큼(BYPASS 최대 덩어리) · **위험** 중(면제를 넓히는 방향이므로 되돌려-관찰 필수)

## 3. 진단 — "느림"은 hop 수가 아니라 산출물 인플레다

12 hop은 그 자체로 느리지 않다 — 대부분 조건부 skip이다. 실제 비용은 세 곳에 있다.

### 3.1 plan.md 659줄 (최대 3923줄)

plan은 **spec의 5.9배**다. 이건 계획이 아니라 사전 구현이다. 그리고 그 659줄이:

- `plan-reviewer-ko` 입력 (읽기 1회)
- `decomposing-ko` 입력 → tasks.md 생성 (변환 1회)
- `dispatch/<task>-context.md` 발췌 (태스크 22개 × 발췌)

로 **재소비된다.** 같은 결정이 spec·plan·tasks·dispatch 4표현으로 존재하고, 넷 사이의 정합은
`validate-structure`가 아니라 **모델의 성실성**이 유지한다.

**조치 후보**: plan.md에 **상한**을 건다(예: spec 줄수의 3배 또는 300줄, 초과 시 WARN→FAIL 래칫).
이 repo는 `skill_size` 래칫으로 이미 같은 기법을 쓴다.

### 3.2 고정 컨텍스트 17.5KB × 매 세션

SessionStart가 메타 skill **본문 전체**를 주입한다. 실제로 필요한 것은 **진입 신호 판정 규칙**뿐이고,
본문은 신호가 잡혔을 때 로드하면 된다. 이 repo에서만 세션당 ~5k 토큰이 신호 판정에 쓰인다.

**조치 후보**: 앵커 + 신호표(~2KB)만 주입, 본문은 `Skill` 호출로 지연 로드.
단 **조립 순서 계약**(`test-session-start-order.sh`가 잠금)을 깨지 않아야 한다.

### 3.3 pre-push의 run-all 전체 — 실측 **758초 (12분 38초)**

이번 검토에서 직접 쟀다: `run-all.sh` → **158 스위트 PASS · real 758.05s · user 343.56s · sys 337.60s**.
CLAUDE.md는 "~600s+"라고 적어 뒀는데 **실측은 758초**다. 이 문서에서 **시간으로 실측한 유일한 항목**이다.

`user+sys = 681s`인데 `real = 758s`라 **거의 CPU 바운드 · 단일 프로세스 직렬**이다 — 병렬화 여지가 크지만
그 판단은 계측(H) 없이는 어느 스위트가 시간을 먹는지 모른다.

도구 무관 게이트로서 필요하다는 판단은 유효하다(계기: 44cd095). 다만 **모든 push마다 12분 40초**일 필요는 없다.

**조치 후보**: pre-push는 **변경 스코프 부분집합**, 전체는 릴리즈 pre-flight에서. 스코프 매핑은
`propagation-matrix.jsonl`이 이미 갖고 있다.

> **계측 부재 고백**: 위 세 항목은 **크기**로 논증했고 **시간**으로는 논증하지 못했다.
> `metrics.jsonl`의 토큰 필드가 6회차 처방 5번으로 삭제됐고(정직한 선택이었다), 그 결과
> **"느림"을 정량화할 계기가 지금 하나도 없다.** 삭제 자체가 틀렸다는 뜻은 아니다 —
> null만 쌓는 필드는 지우는 게 맞았다. 다만 **채워지는 계기를 넣지 않고 지운 것**이 남은 문제다.

## 4. 진단 — 프로세스 타당성

### 4.1 모집단과 기본값의 불일치

실사용 173 FID 중 **유지보수 100(58%)**. 그런데:

- 기본 진입(`/start`, 자연어)은 **신규 12hop**이다
- 경량 경로(`lite`)는 **7%**만 쓰인다
- `maintain`은 `analyzing-ko`(current-state + impact-analysis)를 **선행 추가**한다 — 유지보수가 신규보다 **더 무겁다**

**주 사용 모드가 가장 무거운 경로다.** 이건 기본값이 잘못 잡힌 것이다.

### 4.2 자기소비

self-dogfood FID **72건**, 6회차 구간 신규 능력 라인 **A=0**, 자기유지 라인 **92%**.
5회차가 이미 처방했다 — *"게이트를 검사하는 게이트를 한 구간 쉬어라."* 6회차 구간에도 반영되지 않았고,
이번 구간의 최대 발견(§2.1)도 **게이트 자신의 결함**이다.

이건 도구가 나쁘다는 뜻이 아니라, **강제층이 복잡해서 강제층 유지가 일이 됐다**는 뜻이다.
`governance-lib.sh` 1380줄 · 함수 32개 · 동일 정규식 4사본이 그 증상이다.

### 4.3 3자 사용자 0명 (7회 연속)

star·fork·issue·watcher 0. 한국어 전용 + 의존 marketplace 선행 등록 + 12hop 학습곡선.
**이 축은 이번 검토의 어떤 조치로도 움직이지 않는다** — 여기 적는 이유는 §4.2의 자기소비가
"쓰는 사람이 저자 1명이라 저자가 도구를 고치는 것 말고 할 일이 없다"는 구조와 맞물려 있어서다.

## 6. 이 검토가 하지 않은 것 (다음 사람에게)

- **시간은 `run-all` 758초 하나만 쟀다.** 나머지 "느림" 논증(§3.1 plan 인플레 · §3.2 컨텍스트)은
  **크기 대리변수**에 기대고 있다 — lifecycle 한 바퀴가 실제로 몇 분인지는 아무도 모른다(H가 필요한 이유).
- **B의 이빨 약화 여부를 실증하지 않았다.** 되돌려-관찰(변이 주입) 없이 B를 머지하면 v1.88.0이 고친 병의 재발 경로다.
- **§2.3의 마지막 한 칸이 추론이다.** 커밋 형태 91%가 **보수 판정(working-tree 전체)**으로 떨어지는 것은
  직접 호출로 확인했다. 그러나 **"그때 working tree에 코드 dirty가 실제로 있었는가"**는 확인하지 못했다 —
  과거 세션의 dirty 상태는 git으로 복원되지 않는다. 보수 판정은 dirty가 있을 때만 deny하므로, 엄밀히는
  "**실사용 커밋의 91%가 면제 경로에 진입조차 못 한다**"까지가 실측이고, "그래서 막혔다"는 그 위의 추론이다.
  (lifecycle implement 중에는 working tree가 거의 항상 dirty이므로 추론의 강도는 높다.)
  확정하려면 `pretool-governance.sh`에 같은 형태의 커밋을 dirty 트리에서 통과시켜 보는 재현 1회면 된다.
- **BYPASS 134건 중 62%가 "기타"로 분류됐다.** 사유 문구가 자유서술이라 정규식 분류의 한계다.
  표본으로 보면 대부분 "코드 무변경"의 변형이지만, 전수 확인은 하지 않았다.
- **6회차 처방 1·2(완주 계수기 · batch stall)를 대체하지 않는다.** 그것들은 계측·전파 결함이고 여전히 열려 있다.
